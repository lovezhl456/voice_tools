# NISQA Linux Docker 验收记录

日期：2026-09-20。版本 `0.10.2`，分支 `enhance/v0.10.2-nisqa-docker`，基于主线 `14ed371`（PR #17）。使用本地 Docker 完成安装、下载、真实模型推理和批量 CLI 验证。操作步骤见 [Docker 指南](nisqa-docker.md)，前轮 Mac 结果见 [Mac 验收](nisqa-validation.md)。

## 环境与安装

| 项目 | 实际环境 |
|---|---|
| 宿主 | Apple M1 Max，32 GiB 内存 |
| Docker | Docker Desktop，Engine 23.0.5；Linux VM 5 核、约 7.67 GiB 内存 |
| Linux | Debian 12 / glibc 2.36，LinuxKit 内核 5.15.49 |
| `linux/arm64` | 本机虚拟化执行，已完成真实模型与资源测量 |
| `linux/amd64` | 在该 Mac 上模拟 x86_64 执行，已完成真实模型与专项回归；不作为物理 x86 服务器速度基准 |
| Python | 3.12.14 |
| 主要依赖，两架构相同 | torch 2.14.0+cpu、torchmetrics 1.9.0、librosa 0.11.0、numpy 2.5.3、soundfile 0.13.1 |
| 其他依赖 | numba 0.67.0、llvmlite 0.49.0、scipy 1.18.1、requests 2.34.2 |
| 评分限制 | 2 CPU、2 GiB 内存、禁用额外 swap；PyTorch 2 线程 |
| 运行隔离 | 普通用户、只读根文件系统、只读权重/音频挂载、可写结果目录、512 MiB 临时缓存上限 |

两架构镜像均从官方 Python 基础镜像安装 CPU Torch 和 `.[nisqa]`，`pip check` 通过。`torch.version.cuda` 为 null，未安装 `nvidia-*` 包。没有借用 Mac 的 Python 虚拟环境。

构建上下文约 637 KB，仅允许源码和打包文件；模型、录音、Git 历史、环境及输出不进入构建上下文。镜像检查确认项目目录无权重或音频，运行镜像也未保留下载代理变量。镜像约 **1.42 GB（ARM64）/ 1.51 GB（amd64）**，为本地未压缩大小；单个模型约 1.05 MB，依赖库占据主要磁盘空间。

## 模型与网络

- Linux CLI 在新的宿主目录实际执行 `nisqa download`，返回 `downloaded: true`，文件大小和固定 SHA-256 校验通过。模型来源和非商业许可见 [NISQA 手册](nisqa.md)。
- 本机 Docker Hub 直连超时；本轮通过已有本机代理从 **Docker 官方 Registry** 取得基础镜像，逐项核对 manifest、配置、压缩层及解压层 SHA-256 后导入 Docker。未使用第三方修改镜像，也未修改系统/Docker 全局代理。
- 构建时仅给该次构建传递临时代理参数；权重下载容器首次 TLS 握手超时，重试成功。这个网络问题与模型推理分开记录。
- 评分和专项测试使用 `--network none`。检查确认没有 IPv4 路由，向文档保留地址 `192.0.2.1` 建立连接返回 `ENETUNREACH`。LinuxKit 还显示两个未提供外部路由的默认隧道接口，因此不能仅用“接口名只含 lo”判断断网。
- 断网下再次执行 `download` 对已有正确权重返回 `downloaded: false`，以及 `doctor`、`analyze` 均按预期执行；缺少模型时明确退出，不尝试自动下载。

官方基础镜像 `python:3.12-slim-bookworm` 本轮平台 manifest：

```text

amd64 sha256:1aaa65a85fda306ffb8b910824d4e93bdce61e212c7e87168123ea3073b41a1a
```

## 真实执行矩阵

素材沿用前轮 28.601723 秒的中文合成语音，由它转换成不同采样率/声道，并另外生成静音和损坏文件。它是工程验收素材，不是真实通话或听感标注集。下面各项在两架构上均通过：

| 场景 | 实际结果 |
|---|---|
| 离线 doctor、已缓存权重 download | 退出码 0；不重新下载 |
| 递归单声道批量：8 kHz WAV、16 kHz FLAC、22.05 kHz WAV | 3 文件、9 段真实评分，0 错误；五项分数均有限 |
| 16 kHz 双声道，显式 `--channel both` | 左右声道各 3 段，共 6 段真实评分；声道和时间信息保留 |
| 好录音、静音、损坏 WAV 混合批量 | 3 段已评分、1 条证据不足、1 条处理错误；退出码 3，成功结果保留 |
| 缺少本地权重 | 退出码 2，不创建评分结果目录 |

amd64 的 **22 项 NISQA 专项测试全部通过，无跳过**，耗时 160.353 秒，包含真实模型对齐。测试显式禁止 HTTP，并验证五项输出与 TorchMetrics 1.9.0 公共函数在 `rtol=1e-6, atol=1e-6` 内一致。该耗时包含本机模拟与首次编译，不能外推服务器容量。

ARM64 最终全仓回归 **337 项，313 项执行通过、24 项跳过，93.026 秒**，包含真实 NISQA 对齐。跳过项为 19 个未启用的原生 PJSUA2 本机 SIP 测试、4 个缺少 FFmpeg 的可选测试、1 个 WebRTC VAD 测试。测试使用运行镜像派生的临时测试镜像，额外安装既有测试所需的 Node.js、tshark/mergecap、tcpdump；它们没有进入 NISQA 运行镜像。

全仓检查发现并修正了一处已有测试的跨版本格式假设：Debian 的 tshark 4.0.17 将 `rtpevent.end_of_event` 输出为 `1/0`，新版输出 `True/False`。仅调整测试读取这两种布尔表示，保留对事件数、按键重复和时长的原断言；未修改 SIP 生成数据或 NISQA 评分代码。修正后 Linux 全仓及 Mac 的 16 项 SIP 批量回归均通过。

## ARM64 资源实测

在本任务其他测试与构建结束后，单独启动一个受上述资源限制的运行容器。容器内先执行短素材 smoke，再以新的 CLI 子进程处理同一素材重复 10 次的长文件；两个进程共享该容器的 `/tmp` 特征缓存。两次都使用真实模型，没有处理错误或证据不足。

| 指标 | 新容器首次推理，Numba 缓存为空 | 同容器内后续运行，缓存已预热 |
|---|---:|---:|
| 输入长度 | 28.602 秒 | 286.017 秒 |
| 已评分片段 | 3 | 29 |
| CLI 子进程墙钟时间，含 Python 启动 | 10.306 秒 | 7.427 秒 |
| CLI 内部时间，含运行库/模型加载 | 9.472 秒 | 6.718 秒 |
| 运行库/模型加载 | 1.480 秒 | 1.423 秒 |
| 文件读取、前处理、推理和逐段输出 | 7.992 秒 | 5.296 秒 |
| 子进程峰值 RSS | 657.727 MiB | 560.250 MiB |

墙钟时间不含镜像拉取、构建和 Docker 启动。首次列仅表示该容器的 Numba 缓存为空，宿主文件缓存并未清空；两列输入长度不同，不能直接相减当作启动成本。RSS 是 CLI 进程占用，不是整个容器或 Docker 虚拟机内存。2 GiB 是已通过这组样本的容器限制，不是官方最低配置。

本地原始证据保存在 Git 忽略目录：`outputs/nisqa-linux/arm64-cold-001`、`arm64-warm-001`、`arm64-functional-002`、`amd64-functional-002`，以及 `.local/nisqa-linux-*.log/json`。仓库只保留脚本、部署定义与本记录。

## 验证边界

本轮已覆盖 Linux 容器安装与真实推理，但未验证物理 x86/ARM Linux 服务器的性能、生产规模、长时间稳定性或真实中文通话准确度。CPU 指令、虚拟化、录音长度、采样率、声道、缓存与并发都会影响结果。上线容量应在目标服务器用有权限的代表性录音另测；本地模型执行成功也不改变权重许可。
