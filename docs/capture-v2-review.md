| 问题 | 原行为及影响 | 修复与验证 |
|---|---|---|
| 冻结文件未必关闭 | 以 mtime 排序排除“最新文件”；相同 mtime、空闲但仍打开的文件可能被当作关闭片，冻结时暂时不增长也不能证明完整 | 运行中的任务仅接受 dumpcap `printname` 关闭通知；模拟相同 mtime，并用真实 dumpcap FIFO 回放验证 |

| 窗口前的媒体映射丢失 | 只保留 UUID 最近一条事件；较新的无 flow 事件覆盖了此前有效四元组 | 同时保留最近媒体观测与生命周期观测，保留各自时间 |
| SIP 分叉被全局截止 | 任一 BYE 触发全局导出截止，另一分叉的后续 RTP 被排除 | 按匹配媒体阶段决定窗口，开放分叉继续保留候选媒体 |
| 反向 re-INVITE 未替换旧阶段 | 对端发起请求时 From/To tags 交换，旧端点阶段仍无限延续 | 用发送端＋无序 dialog tags 标识同方向阶段 |
| 过期快照被挂机事件延长 | 原采样覆盖到 15 秒，100 秒的挂机把覆盖错误延长至 100 秒 | 挂机只缩短窗口；另覆盖“PCAP 早于快照但位于采样窗口内”的导出场景 |
| 单侧 SRTP 声明未保护反向流 | 只有发送端的 SAVP SDP 时，反向目的端没有 SDP，可能按静态 G.711 解码密文 | 任一已观察端点的有效 SAVP 阶段都阻止相关双向解码；codec 映射仍按接收端 |
| 非首包时间戳回退未拒绝 | 时间戳 1000→1320→1160 均不早于首包，因此旧实现仍标 ok 并裁剪重叠音频 | 按序号排列后逐包检查单调性，不能可靠重建则明确 unsupported |
| 不同通话复用端口/SSRC 被合并 | 两个已知 Call-ID 的导出按 sensor 合并，后一个通话可能变成重复包或音频被丢弃 | 报告以 sensor＋已知 Call-ID 分组，不改变同一通话的跨分片连续统计 |

## 进一步修补的边界

- **快速轮转与文件淘汰**：不因扫描时文件被轮转删除而终止整个采集；大小轮转已覆盖请求末尾时立即冻结，避免固定等待时间轮转期间证据已被覆盖。关闭通知计数辅助识别第一次目录扫描之前发生的淘汰。
- **日志和冻结额度**：dumpcap 即使使用 `-q` 仍输出每次轮转的文件名，因此 stderr 也限制为两份各 1 MiB。损坏事件按一条 gap 摘要记录，避免短坏行放大为大量诊断输出；复制期间事件日志增长时再次检查实际冻结字节，超额保留 PCAP 和映射缺口回执。
- **启动中断恢复**：远端路径在首次 SSH 创建操作前写入本地原子 job.json。即使 SSH 回执丢失或部署中断，也有明确恢复位置。窗口模式中断后尝试停止，并要求按结果确认。
- **心跳与时钟**：用远端读取时刻减远端更新时间判断过期，避免仅因两机时钟有偏差就标 unresponsive；跨主机媒体对时仍需验证时钟同步。
- **事件缺口**：损坏事件不再使已复制 PCAP 失去回执；无 Call-ID 的快照保留为不完整映射证据。
- **计数与传播**：区分采集点总丢弃、libpcap 丢弃、dumpcap 内部丢弃及接口丢弃；不把总丢弃都标成内核丢包。直接导入裸 PCAP 时，截断状态也传播到索引和后续导出。
